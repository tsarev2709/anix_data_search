# Эксплуатация

## Скоринг

Баллы складываются из проверяемых признаков:

| Признак | Баллы |
|---|---:|
| ФИО | +10 |
| должность | +5 |
| ФИО + должность в официальном источнике | +20 |
| совпадение с целевой ролью | +20 |
| персональный email на официальной странице | +40 |
| персональный email в другом публичном источнике | +25 |
| личный Telegram с официальной страницы | +35 |
| публичный личный Telegram | +20 |
| профессиональный профиль | +20 |
| VK / Threads / Instagram | +12 |
| общий email | +10 |
| email подтверждён | +20 |
| confidence Hunter от 70% | +10 |
| телефон | +8 |
| официальный источник | +8 |
| Hunter с источником | +8 |
| независимый веб-источник | +5 |
| минимум два URL | +5 |
| источник моложе двух лет | +10 |
| источник старше четырёх лет | −20 |
| email построен по шаблону | −30 |
| домен не имеет MX | −30 |
| email недоставляемый | −100 |

Порог по умолчанию — 35. Если ни один общий адрес не прошёл порог, но на официальном сайте есть `info@`/`office@`, один такой адрес добавляется как fallback. Он явно маркируется в отчёте.

## Дедупликация

- внутри запуска кандидаты объединяются по нормализованному email;
- перед записью AmoCRM ищется точное совпадение email или телефона;
- найденный контакт переиспользуется;
- уже связанный со сделкой контакт повторно не привязывается;
- после полного успеха исходная сделка перемещается в следующий этап.

Последний пункт обязателен для устойчивой работы `new_lead`. Без `AMO_SUCCESS_STATUS_ID` одна исходная сделка останется в очереди и может создать новые сделки повторно.

## Ошибки

Сбой одного провайдера не останавливает исследование компании. Он попадает в `warnings`, после чего используются оставшиеся источники. Сбой записи одного контакта помечается как `failed`; исходная сделка в успешный статус не передвигается.

Если запуск красный:

1. скачать JSON-отчёт из артефакта;
2. найти `actions[].status = failed` и предупреждения компании;
3. исправить токен, лимит провайдера, ID поля или недоступный сайт;
4. повторить эту порцию через `workflow_dispatch` сначала в `dry-run`;
5. затем выполнить `apply`.

## Статусы email и публичные данные

`FOUND` означает, что адрес буквально присутствует в сохранённом evidence. `GENERAL` — буквально найденный общий адрес (`info@`, `sales@`, `hr@` и подобные). `INFERRED` строится только при наличии наблюдаемого корпоративного шаблона, получает штраф и показывается как гипотеза; такой адрес не может быть единственным прямым каналом и перед записью в AmoCRM удаляется.

Проверка MX говорит только о способности домена принимать почту и не называется проверкой конкретного mailbox. Система обрабатывает только публично опубликованные деловые данные, не входит в аккаунты, не обходит CAPTCHA/authentication и не использует утечки. Ответ Hunter `451 claimed_email` приводит к исключению адреса. Сырые отчёты хранятся как приватные артефакты Actions 90 дней; срок можно уменьшить в workflow.

## Наблюдаемость

В Markdown/JSON, Supabase и dashboard сохраняются: запросы, search results, URL сайта и архивов, страницы crawl, sitemap/RSS/PDF/WordPress/JS diagnostics, статусы всех providers, ошибки, social profiles, все кандидаты, отклонённые кандидаты и объяснение балла. Метрики запуска включают ФИО, должности, найденные/персональные/inferred email, телефоны, Telegram, social breakdown, high/medium/low confidence и provider failures.

Радар спроса хранит `first_seen_at`, `last_seen_at`, запрос, источник, автора, score, прямые каналы и решение пользователя. Повторное обнаружение того же URL обновляет запись без дубля. Исторические запуски контактов сохраняют `published_at`, `discovered_at` и `last_seen` для сравнения новых назначений, публикаций и изменений sitemap/RSS.

## Следующие улучшения

1. Метрики ответа по источнику и роли для обучения скоринга на данных Anix.
2. Временной cooldown и повторная проверка контакта через 60–90 дней.

4. Персонализированный черновик первого касания на основе компании, сигнала спроса и найденной роли.
5. Telegram MTProto и VK API для поиска внутри публичных постов без зависимости от web-индекса.
